# 桌面测试

## 定义

桌面测试模块通过独立原生应用执行功能验收与显示性能测量。

## 参考

### 拥有

- `scripts/desktop/`：独立构建、统一运行入口、应用寿命、样本、场景及报告。
- `src-tauri/tauri.desktop-testing.conf.json`：测试应用标识、原生窗口和调试参数。
- `src/test/desktop/`：注入真实 WebView 的页面探针。
- `tsconfig.desktop-scripts.json`：桌面驱动的 Node 与 DOM 严格类型环境。

### 消费

- `schemas/spec-defaults.json`：沉浸式性能样本的规格默认内容。
- `scripts/shared/performance-samples.mjs`：与浏览器一致的 CSV、文本、候选及联合编辑文件样本。
- `scripts/shared/performance-scenarios.mjs`：共同场景身份与沉浸式编辑目标。
- `scripts/shared/sample-statistics.mjs`：正式测量的统一统计。
- `scripts/shared/test-output.mjs`：排他报告、构建哈希及 JSON 与 Markdown 交付。
- `scripts/shared/test-report.mjs`：公共检查、性能结果及可读报告。
- `scripts/shared/test-workspace.mjs`：排他工作区、报告预留及目录释放。
- `src-tauri/tauri.conf.json`：正式应用的基础构建与装配配置。
- `src/app/`：真实桌面窗口、组件与输入。
- `src/domain/`：页面探针读取的正式展示模型。
- `src/shared/lib/starsector/`：首表名称、值展示与 Mod 版本格式的正式规则。
- `src/shared/types/`：正式运行协议及业务模型。
- `tsconfig.base.json`：共同严格类型约束。

### 装配

- `eslint.config.js`：桌面脚本的完整类型检查装配。
- `package.json`：桌面构建、场景执行、资源测试及类型检查入口。

### 关联

- `CONTRIBUTING.md`：桌面测试的正式命令与参数说明。

## 边界

- 桌面运行持有本次原生进程及调试连接，默认使用当前用户桌面，隐藏模式附带独立 Windows 桌面。
- 来源同步、编辑器生命周期与性能、CSV 显示及来源性能场景消费同一启动、就绪和正常关闭流程。
- 样本工作区持有生成或复制的游戏与 Mod 文件。
- 页面探针消费真实组件与数据模型；来源性能在页面就绪后通过直接 CDP 连接观测，并释放浏览器驱动的网络响应保留。
- 报告持有每次运行的结果、诊断、日志、截图、进程采样与堆快照。
- 统计工具与排他目录工具保持公共属性。
- 原生场景归 `scripts/desktop/cases/`，共同消费应用寿命、样本和报告；页面内测量归所属页面实现。

## 链路

### 构建与执行

1. 构建入口读取桌面测试配置并交付独立 Cargo 产物。
2. 执行入口预留报告并建立样本工作区。
3. 运行基础核对调试端口并排他创建工具及 WebView 目录。
4. 原生宿主按运行参数在当前用户桌面或独立 Windows 桌面启动应用，驱动连接真实窗口并等待应用就绪。
5. 所属场景执行来源同步、编辑器生命周期与性能、CSV 显示或来源性能检查，来源性能分别采样单会话、双会话和混合负载。
6. 所属应用经正常关闭交付日志并释放连接与工具目录。
7. 样本工作区释放，报告交付 JSON、Markdown 与实际退出码。

## 规范

- 桌面测试必须使用独立应用标识、构建目录、工具目录及 WebView 资料目录。
- 默认运行使用当前用户桌面，`--isolated-desktop` 启用独立 Windows 桌面并将全部子窗口放入该桌面；宿主严禁切换用户输入桌面，应用消费正式显示与聚焦流程。
- 宿主必须使用 Windows 普通用户权限令牌启动测试进程，所属桌面授权覆盖当前用户及 WebView2 沙箱。
- 原生宿主必须在应用退出后释放所属进程及创建的桌面句柄；原生验收必须核对所选桌面与线程内输入焦点，隐藏模式共同核对系统输入桌面的前台焦点。
- 原生启动失败必须交付进程原始输出及退出码，重试必须保持所选桌面模式。
- 样本必须在排他工作区内生成或复制，文件动作只允许作用于本次样本。
- 显式报告输出必须排他预留，已有文件及目录完整保留。
- CSV 性能默认测量 30 次，视口为 1360×860、DPR 1.5，记录可视字段、引用名称及图片就绪的实际采样与统计。
- 重复采样默认预热 2 次、正式测量 30 次，预热与正式样本分别登记，首次打开独立记录。
- 工作区打开消费明确的 Mod、游戏目录或生成样本；指定目录按原路径读取，元数据、目录数量及首表由正式结果交付，各项目执行一次；目录选择结果由驱动提供，后续识别、会话及界面走正式流程，工作区和实际可用首表就绪分别记录耗时。
- 工作区打开在独占工具目录启用现有性能监视，记录空工具缓存及保留的系统缓存；命令按请求身份关联后端耗时，原生阶段与时间线附件随报告交付；页面逐帧核对就绪并等待随后两帧，动作发送、响应至状态就绪、绘制帧等待及驱动观测分别计时，并行后端区间按并集合计。
- 沉浸式性能必须覆盖舰船、皮肤、武器、战机联队和装配；自包含 Mod 样本以无关装配文件数表达规模，重复采样采用 1280×860、DPR 1.5，首次读取与预读后的首次窗口打开分别记录。
- 沉浸式读取计至正式联合查询返回，保存计至实际字段提交后的写盘值及已保存状态接纳和随后绘制帧；IPC 响应、命令次数、一次项目保存及窗口目标释放共同交付。
- 武器、战机联队与插件选择测试从真实装配窗口打开候选，记录打开、滚动、选择与关闭，并核对候选数量及装配写盘结果。
- 文本编辑器采用共同内容与首尾交替编辑，保存后执行三轮撤销重做并逐步核对完整文本，记录阶段内存及目标释放。
- 页面探针必须在字段及可视资源就绪后消费随后绘制帧，原始样本与统计共同交付；来源性能必须在驱动交接后及负载完成时核对所属连接维持的实际视口、布局与 DPR。
- `--dry-run` 必须交付实际执行配置，严禁创建目录、启动应用或写入报告。
- 功能检查必须交付 checks，性能场景必须交付 runs，参数单位、操作与完成条件、实际样本及资源释放必须随报告交付。
