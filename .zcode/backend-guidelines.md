# Backend Guidelines

本文档只规定 Rust 后端代码的通用写法、通用设计判断、测试和注释规则。项目层级、能力所有权、业务状态、外部协议和具体调用链见 `.zcode/overview.md` 或所属模块文档。

## 代码组织

- 依赖必须在所属模块顶部通过 `use` 导入；跨业务模块引用必须以该导入作为使用点名称，并保留对应平台与功能条件；函数、闭包和普通代码块内严禁声明 `use`。
- 使用点必须采用已导入类型或最多一层模块限定的函数名称，严禁展开 `crate`、`super`、`self` 或多层模块路径；类型关联函数、枚举成员和原生类型关联项必须保留类型限定。
- 跨业务模块传递的类型必须按其声明名称直接导入；业务函数通过所属模块命名空间调用。
- 业务模块出口必须直接指向实际声明；转导出层数最多一层，跨模块转导出必须保留实际定义位置。
- 宏定义及生成代码中的路径必须按展开位置的名称解析与宏卫生要求表达。
- 文件、模块和函数名称分别使用 `snake_case`；类型和 trait 使用 `PascalCase`；常量使用 `UPPER_SNAKE_CASE`。
- 代码按职责边界组织；拆分依据是独立状态、输入输出、错误或生命周期责任，代码行数不能单独决定拆分。
- commands 中的生产函数必须声明统一 command 宏；业务执行与辅助函数必须归所属服务维护。
- 业务动作严禁按参数生成另一套业务函数；转接层必须承担明确的授权、内容变换、等待或生命周期工作。
- 纯规则与转换保持无副作用；外部 IO、协议转换和业务编排分别保持清晰边界。
- 公开名称表达能力、数据或 owner；禁止使用无法表达职责的占位缩写。
- 跨模块调用必须经正式公开接口；调用方不能绕过所属 owner 直接修改内部状态。
- 会话生命周期与业务能力必须分别交付；业务函数必须由服务装配直接导出，会话根严禁聚合查询、资源和业务保存入口。

## 类型与分支设计

- 互斥且封闭的状态使用一个明确的判别类型表达；开放集合使用可扩展的数据结构。
- 类型选择必须与值域、跨层协议和生命周期一致；禁止为了减少文件数量把不同语义压进同一类型。
- 多分支处理先判断同构程度：输入、输出、状态和生命周期一致时优先使用一个统一分派函数。
- 分支拥有不同不变量、错误语义或生命周期时，必须拆为分别命名的函数；仅有少量重复代码不能作为合并理由。
- 抽取 helper、adapter、trait、泛型或参数化函数前，必须证明共享不变量成立，并且能减少公开入口、状态 owner 或重复生命周期逻辑。
- 同类问题优先复用已有同类实现，并保持同类模块的结构一致；领域差异必须保留在明确的分支边界。

### 类型名称

- 类型名称必须优先表达实际业务产品；列表条目、目标索引、场景和面板必须使用对应产品名。
- Snapshot 必须表达同次捕获的内容、身份或版本；State 必须表达持续变化的值；Runtime 必须拥有所属寿命内的状态和动作。
- Ticket 必须表达可撤销的读取接纳权；Lease 必须表达需要释放的持有权；Task 必须表达进行中的工作及其完成条件。
- 纯编辑差异必须以 Edit 表达并由所属历史流程回放；Request 必须表达业务请求，Payload 必须表达原生命令参数。
- 更新包必须在实际变化交付边界装配；清单查询必须直接交付正式清单，读取门控必须以就绪状态命名。
- 完全同义的类型别名必须直接复用正式声明；类型改名必须同步字段、方法、工厂、文件、消费者、协议和检测器。

## Rust 惯用法

- `Option` 与 `Result` 优先使用 `map`、`and_then`、`ok_or`、`filter_map` 等组合操作表达转换和失败传播。
- 边界类型转换实现 `From` 或 `TryFrom`；调用方使用 `?` 传播失败，禁止散落重复转换函数。
- 语义值使用 newtype 或明确结构承载；禁止在使用点反复解释裸字符串或裸数字。
- 非测试路径禁止 `unwrap()`；`expect()` 只用于已经建立的不变量，并说明该不变量。
- 异步函数必须显式等待异步操作；禁止把阻塞操作隐藏在看似同步的公开接口中。
- 序列化结构必须明确公开字段语义；协议字段变化必须同步类型、消费者和验证。

## 错误处理

- 错误必须保留足以定位问题的上下文，包括输入来源、路径、记录位置或操作阶段。
- 解析、校验和外部 IO 失败必须显式传播；禁止用默认值掩盖结构错误。
- 错误包装必须保留原始原因和稳定语义；展示文案由消费层决定。
- 失败路径必须保留必要的调用上下文，不能在错误映射中静默丢失诊断。

## 测试

- 新增解析、归一化、分支分派、错误转换和持久化边界必须补充成功与失败行为测试。
- 测试断言公开行为、输出协议和错误语义；禁止复制生产实现内部步骤作为唯一断言。
- 文件测试必须由 TestWorkspace 排他持有所属外层目录；业务目录、外部来源及改名位置必须位于所属工作区内，文件必须保留准确名称。
- 测试正常结束必须显式完成所属释放；失败兜底必须分别记录原始错误和释放错误，析构严禁再次 panic。
- 业务测试必须由所属业务测试入口释放其登记状态，再交还文件工作区；全进程配置测试必须在独立子进程内执行，同一缓存样本必须持有所属目录并完成重开验证。
- 同构实现使用参数化测试覆盖同类输入；不同语义使用独立测试表达差异。
- 涉及文件加载、数据读取、解析或对象构造的测试，必须按所属资源身份、有效期和生命周期断言实际执行次数。
- 复用行为测试必须覆盖连续调用与并发调用，验证共享范围内的实际操作只执行一次，并验证失效后的首次调用重新执行一次。
- 所有测试数据必须彻底脱敏，严禁将用户输入或展示的错误例子用于项目内测试数据。

## 注释

- 注释使用英文，优先通过名称、类型和结构让代码自解释。
- 必须在外部协议、冻结常量、算法不变量、顺序敏感边界、重点性能优化位置和 workaround 处添加注释。
- 注释只允许说明设计意图、为什么选择这种实现方式、为什么不选择某种看上去很显而易见的另一种实现方式。
- 禁止复述代码、记录历史过程、保留无追踪目标的 TODO/FIXME 或注释掉的代码。
- 公开接口使用 doc comment 说明输入、输出和失败语义；普通行注释说明约束或意图。
